## 0. 버전 혼합 — 잘못된 소스에서 추출한 베이스

**증상**: 시즌 선택 화면 이미지 깨짐 + 프리징. 구조 검사(STRING/DEC_SIZE)는 다 통과.

**원인**: 초기 추출본 `RES_추출원본`이 **실행 중인 게임과 다른 버전의 RDB에서 뽑은 것**이었다.
`APPSELECT.CHK` 대조로 확정 — 추출원본 body md5 `18f1ec99…` ≠ 실제 RDB 슬롯 `7fef4a79…`,
압축 크기도 866,602 vs 1,313,276 으로 상이. 이 오래된 베이스에 한글을 넣어 최신 RDB에 밀어넣으니
**버전 혼합**이 되었고, 2025년도 업데이트 콘텐츠인 시즌 선택이 깨졌다.
(당시 "STRING CHK 62개가 원본과 DEC_SIZE 다름 — L2D_SUC_0046이 1258896→734064로 반토막" 을
오염으로 의심했으나, 실은 버전 차이였다.)

**조치**: `REINJECT_TRUE_BASE.py` — 추출본 오프셋을 전부 폐기하고,
**실제 배포될 RDB의 슬롯 본문에서 일본어 문자열을 NUL 경계로 검색해 제자리 치환**하는 방식으로 전환.
이후 모든 주입 도구가 "진짜 베이스" 원칙을 따른다.

> **교훈**: 오프셋은 특정 바이너리에만 유효하다. 추출 시점의 파일과 주입 대상 파일이
> **바이트 동일함을 md5로 증명**하기 전에는 오프셋 기반 주입을 하지 말 것.
> 지금은 `SETUP_WORKSPACE.py`가 원본 4파일 MD5를 강제 검증한다.

## 1. 폰트 인코딩 이중화 — 선수명이 깨지던 근본 원인

**증상**: 펜넌트 로스터 UI의 선수명이 `쓰핀땍꼿`(=모이넬로), `윰ㅇ힛꽝`(=야마카와) 처럼
**한글이긴 한데 다른 글자**로 나옴. 다른 화면은 정상.

**원인**: 인코딩 테이블이 **두 개**였다.

| 대상 | 인코딩 테이블 | 매핑 예 |
|---|---|---|
| CHK 주입 (SEN/NXSUR/REINJECT) | `실황2024.wReplace` | 가 → 一 |
| exe 주입 | `hangul_to_hanja.tsv` | 가 → 亜 |

그런데 **실제 렌더는 어느 폰트가 하느냐로 결정된다.** 로스터 UI는 `COMMON_2D_ADD`(ADD 폰트)로
렌더되는데 그 폰트의 글리프 배치는 tsv 기준이다. wReplace로 인코딩한 문자열을 tsv 폰트로 그리니
글자가 어긋난 것. 교차 디코드 `wReplace⁻¹(tsv(화면))` 로 확증했다(모이넬로 → 모이네때).

폰트 실측 결과:
- **ADD 폰트(`COMMON_2D_ADD`) = FNTL/FNTS 둘 다 정확히 tsv**
- **폰트B(당시의 `COMMON_2D` 한글판) = wReplace도 tsv도 아닌 어긋난 제3의 매핑**(±1 시프트 흔적) → 폐기

**조치**: `BUILD_FONT_TSV.py` — 새 메인 폰트 = 원본(전 셀 한자) + tsv에 해당하는 셀에만
ADD 폰트의 글리프를 복사(오프셋 델타·메트릭 포함). **두 폰트 모두 tsv** 가 되어
인코더가 `hangul_to_hanja.tsv` 하나로 단일화됐다.
이후 `RECODE_PASS1/PASS2.py` 로 배포 RDB 전체를 재인코딩(48,859 occurrence / 596 슬롯).

**⚠ 파생 함정 (글리프 오프셋 델타)**: UNCDFONT 레코드가 가리키는 오프셋에서
실제 비트맵은 **FNTL은 −6바이트, FNTS는 ±0** 위치다. 이걸 모르면 추출/비교 시 초성이 밀려
"발"이 "갈"로 보이고, 폰트가 잘못됐다고 오판하게 된다.

**⚠ 파생 함정 (검증 대상 파일)**: SEN_MAIN(2024 로스터)만 재인코딩·검증했는데
**화면이 실제로 쓰는 파일은 `SEN_MAIN_2ND`(2025년도 로스터)** 였다. 그래서 수정했다고 믿은 뒤에도
계속 깨져 보였다. 이후 `RECODE_ALL2.py`는 **파일 리스트 제한 없이 전 슬롯(13,431)** 을 대상으로 한다.

> **교훈 1**: 인코딩 테이블은 **반드시 하나**여야 한다. 두 개면 언젠가 반드시 섞인다.
> **교훈 2**: "어느 폰트로 렌더되는가"는 추측하지 말고 **화면 캡처를 역디코드해 검증**하라.
> tsv_inv 시뮬레이션이 관측과 정확히 일치하면 그게 렌더 주체다.
> **교훈 3**: 로스터·연도별 데이터는 **화면이 실제 쓰는 최신 파일(`*_2ND`)** 로 검증할 것.

## 2. 매달린 UTF-8 리드바이트 — `〓` 와 텍스트 겹침

**증상**: 크래시는 없으나 대사 중간에 굵은 `〓` 가 나오고, 그 지점부터 **텍스트가 겹치거나
페이지가 넘어감**. 타이틀에 내부 ID(`CHE_assign_player`, `PEN_shop_item_00`,
`VersusModeSelectProc` 등)가 그대로 노출되기도 함.

**원인**: 절단 코드가 잘못됐다.

```python
# ❌ 잘못됨 — 연속 바이트만 제거하고 리드 바이트는 남긴다
nb = nb[:ln]
while nb[-1] & 0xC0 == 0x80: nb = nb[:-1]
```

`☆` = `e2 98 86` 이 `e2` 에서 잘리면 그 `e2` 가 남는다. 렌더러는 `e2` 를 3바이트 문자의 시작으로
읽어 **뒤따르는 NUL 종료자까지 삼키고** 다음 문자열까지 계속 읽는다(bleed-in).
exe 잘림 35,913건 중 **34,251건**이 이 상태였다.

**조치**:

```python
# ✅ 유효 UTF-8이 될 때까지 줄인다
nb = kob[:ln].decode('utf-8', 'ignore').encode('utf-8')
# 또는 (현재 BUILD_FROM_MASTER.fit)
while nb:
    try: nb.decode('utf-8'); break
    except UnicodeDecodeError: nb = nb[:-1]
```

이미 배포된 빌드에 남은 684건은 `FIX_DANGLING.py`로 문자열 영역 전역 스윕했다.
⚠ 이때 **원본과 다른(=주입된) 문자열만** 수리해야 한다 — 맹목 스윕이면
`.rodata`의 정상 바이너리 상수 **58,255건을 손상**시킨다.

> **교훈**: 멀티바이트 문자열 절단은 "연속 바이트 제거"가 아니라 **"디코드 성공까지 축소"** 다.
> 그리고 사후 수리 스윕에는 반드시 "원본과 다른 것만" 이라는 안전장치를 걸어라.

## 3. 栄冠나인 멈춤 — 바이너리 오탐 주입 (417k 복원)

**증상**: 栄冠ナイン(고교 육성 모드) 관련 진행에서 멈춤.

**원인**: 텍스트 추출기가 **NUL 경계 + UTF-8 디코드 가능** 만으로 문자열을 판정했다.
순수 바이너리 컨테이너(`CPOMDHDSK`, `HIIV`, `HISNAP`, `FES_IC` 등)의 임의 바이트가
우연히 UTF-8 CJK로 디코드되어 "일본어 문자열"로 추출되고, 한글로 덮어쓰여 **데이터가 파괴**됐다.

**조치**: `AUDIT_BOGUS.py` + `_plaus.py` 로 RDB 전 슬롯의 diff 세그를 감사.
판정은 **유니코드 블록 화이트리스트**(가나/한자/전각/기호/PUA 글리프) 기반이며,
**가나가 0개면 한자는 실코퍼스에서 확인된 REAL_KANJI(가나 포함 문자열에 등장한 2,215자) ∪ 호환한자만 인정**.

- **1,079 슬롯 / 417,014 세그를 원본 복원**
- 栄冠 관련 파일(HSIM/HATK)의 슬랙 사용 110건은 클린 재절단
- 과복원 되돌리기 2종: 텍스트성 파일(NAME_DIC KANJ 청크/SEN_\*/PEN_\* 등 108파일)은 무조건 재주입(5,334세그),
  바이너리 파일은 **가나 포함 + plausible v2 + 사전 매칭** 3조건을 모두 만족할 때만 재주입 → **19파일 30세그뿐**.
  이 비대칭이 40만 복원의 대부분이 진짜 잡음이었다는 방증이다.
- exe는 `.rodata`가 진짜 문자열 풀이므로 lenient 판정(한자-only + `%d億` 같은 ASCII 허용) → 복원 595건에 그침.

초기 시도였던 **정규식 화이트리스트(`OK_RE`)는 실패**했다 — `♥◆Ω`·PUA(투구폼 글리프)·개행이 든
진짜 문자열을 오판했다.

> **교훈**: "UTF-8로 디코드된다"는 텍스트의 증거가 아니다.
> **RDB 바이너리 컨테이너는 strict(가나 필수) + 블록 화이트리스트**,
> **exe `.rodata`는 lenient** — 컨테이너 성격에 따라 판정 기준을 달리하라.
> 정규식보다 유니코드 블록 기반이 안전하다.

## 3b. 栄冠나인 멈춤 2차 — printf 지정자 손상

**증상**: 위 수정 후에도 "선택하면 느려지다 멈춤"(런어웨이).
구조 검사(STRING/DEC_SIZE/재배치/NUL)는 전부 통과.

**원인**: 주입된 exe 서식 문자열의 **`%` 지정자가 원본과 불일치**(747건).

| 유형 | 예 |
|---|---|
| 절단으로 지정자 소실 | `%s勝%s敗%sセーブ` → `%s승%s패` |
| 오역으로 지정자 중복 | `春…%s勝した` → `…%s%s승`, `＆%d本塁打` → `&%d%d홈런` |
| 이스케이프 오류 | `%d` → `%%d` |

⚠ **지정자가 늘어나는 것(KO > JP)이 치명적**이다. printf가 존재하지 않는 인자를 `char*` 로 읽어
가비지 포인터를 역참조한다 → 런어웨이/크래시. 고시엔 통산 성적 표시가 이 패턴이었다.

JSON의 `ko` 자체는 지정자가 정확했다(불일치 0) — **주입 단계에서 손상**된 것.

**조치**: `FIX_FORMAT_EXE.py` — 지정자 토큰은 보존하고 리터럴만 이진 탐색으로 절단하는
`enc_fit`으로 재주입. `ko`의 지정자가 `jp`와 다르면 원문 복원.
오프셋 미매칭 잔여 39건은 최종 전수 스캔으로 일본어 복원.
결과 **exe 서식 지정자 초과 0 / 불일치 0**. (safe20 → safe22, md5 `9203a5b2`)

> **교훈**: 번역·절단 어느 단계에서든 **`%` 지정자의 개수·타입·순서를 보존**하라.
> 특히 **지정자 추가는 절대 금지**. 주입기의 절단 로직이 지정자를 인식해야 한다.

## 4. exe redirect v1 — 죽은 zero-run 풀 오판

**증상**: 게임 시작 후 ~9.7초에 크래시. `va=0xADACABAAA9A8A7A6` 로 코드 점프
(값이 `A6 A7 A8 A9 AA AB AC AD` — 명백한 연속 증가 패턴 = 인접 데이터를 포인터로 읽은 것).

**원인**: `.rodata`의 zero-run(연속 0 영역)을 "빈 공간"으로 보고 문자열 풀로 썼는데,
**기존 포인터 12,841개가 그 zero-run 내부를 가리키고 있었다**(한 블록에만 1,005개).
한글 UTF-8로 덮어쓰자 그 포인터들이 가비지를 가리키게 됨.

**조치**: `SAFE_REDIRECT.py` (v2) — 풀 후보에서
(1) 데이터 포인터의 타깃 내부 run 배제, (2) `ADRP`/`ADR` 코드 참조가 걸린 `.rodata` 페이지 배제,
(3) 양끝 32바이트 예약 + run ≥ 64바이트 조건만 사용 → **1.95MB의 "죽은 바이트" 풀** 확보.
검증: `.text`/`.data`/헤더 바이트 불변, 풀 기록 1.27MB가 전부 원본·베이스 양쪽에서 0인 죽은 바이트,
재작성한 67,391 워드가 전부 진짜 `char*`(24B 레코드의 3번째 필드).

> **교훈**: **"0이면 비었다"는 거짓**이다. 0 영역은 누군가의 타깃일 수 있다.
> 풀 후보는 "0인가"가 아니라 **"아무도 가리키지 않는가"** 로 판정해야 한다.
> 그리고 이 교훈조차 §6에서 다시 부족했음이 드러난다.

## 5. nnrtld 부팅 크래시 — "24B 레코드"는 사실 DT_RELA 엔트리였다

**증상**: 접합부 정비(safe9~15) 후 게임이 **로더에서 사망**.
`Invalid memory access (PC = nnrtld:0x8f4)`. 부팅조차 안 됨.

**원인**: 대사 조각 테이블을 `[char*, ptr, 0x403]` 형태의 "24바이트 레코드"로 인식하고 편집해 왔는데,
그 영역은 실제로는 **MOD0 dynamic의 `DT_RELA` 재배치 테이블**이었다.

```
DT_RELA = 0x2ab0058,  RELACOUNT = 0xc36e2 (= 800,482개 R_AARCH64_RELATIVE)
Elf64_Rela { u64 r_offset, u64 r_info = 0x403, u64 r_addend = 문자열 VA }
```

내가 "레코드"라고 부르며 8바이트를 쓴 위치들은 **엔트리 경계(`rela_fo + 24*k`)에 정렬되어 있지 않았다.**
미정렬 write는 인접 엔트리의 `r_offset`/`r_info`까지 덮어썼고, 로더가 로드 시
`*(base + 손상된 r_offset) = ...` 를 수행해 엉뚱한 주소에 썼다.

추가로, 접합부 "죽은풀" 스캐너가 **이 재배치 테이블의 0 값(addend 등)을 dead run으로 오인**해
문자열을 써넣은 것도 손상원이었다.

**조치**: `clean8` = safe8의 동적 영역 `[0x2aafb79, 0x3d2551d]` 을 부팅 확인된 safe6으로 복원
(= 재배치 테이블 원복, 문자열 영역 번역은 유지). 그 위에 `REBUILD_INPLACE.py`로
접합부를 **문자열 제자리 편집만**(재배치 테이블 무변경, `DYN_HI` 초과 오프셋만) 재적용.
검증: 동적 영역 변경 0, `.text`/헤더 변경 0. → main-safe20 (md5 `4455950f…`, fallback clean8 `b410bce8…`)

> **교훈**: **`[0x2aafb79, 0x3d2551d]`(DT_RELA/JMPREL/HASH/GNU_HASH/SYMTAB/STRTAB)은
> 절대 풀로 쓰지 말고, 미정렬 write를 하지 말 것.**
> 단, **`r_addend`를 24바이트 정렬해서 바꾸는 재포인팅은 정상 재배치이며 부팅에 안전하다**
> — 이것이 나중에 꼬리풀 리다이렉트의 근거가 된다.
> 그리고 **"이건 무슨 구조인가"를 추측으로 이름 붙이지 마라.** `.dynamic`을 파싱해서 확인하라.

## 6. 죽은풀(dead pool) — 셰이더 크래시

**증상**: 게임 시작 **19초**(초기 렌더 시점)에 GPU 크래시.
`va=0xFFFFFFFFFFFFFFFF`, Ryujinx `ShaderCache.GetGraphicsShader`.

**격리(이분법)**:

| 조합 | 결과 |
|---|---|
| v1.0 main + v1.1 RDB | 정상 → **main이 원인** |
| main_no_redirect (리다이렉트만 제거, 씬 재번역·루비 유지) | 정상 → **마이라이프 리다이렉트가 원인** |

**원인**: §4의 교훈을 적용해 "안전한 죽은풀"을 만들었다 —
코드 `LDR`/`ADR`/`ADRP` 참조 배제, 데이터 포인터 배제, RELA addend 배제.
그럼에도 그 안에 **셰이더/리소스 디스크립터 테이블의 0 필드**가 섞여 있었다.

> 게임이 그 데이터를 **`base + index`** 로 접근하기 때문에,
> **개별 포인터를 아무리 검사해도 걸리지 않는다.**

거기에 대사 문장을 써넣자 초기 셰이더 주소가 오염됐다.
PoC(51바이트 1건)는 우연히 안전한 위치라 통과했으나, 전체(318KB) 적용에서 위험 영역을 포함했다.

**조치**: v1.1 릴리즈의 main을 `main-new`(리다이렉트 제거, md5 `fc473705`)로 교체 배포.
씬 재번역·루비·선수명 개선은 유지.

> **교훈**: **exe `.rodata`의 죽은풀은 재사용 금지.**
> "포인터가 안 가리킴"은 안전의 충분조건이 아니다 — `base+index` 접근 데이터가 존재한다.
> 정적 분석으로 "아무도 안 쓴다"를 증명할 수 없는 영역에는 아무것도 쓰지 마라.
> 검증은 **PoC 1건이 아니라 전체 규모로** 해야 한다.

## 7. 세그먼트 재배치 확장(EXPAND_NSO) — 마이라이프 28일차 크래시

이 프로젝트 최대의 실패이자, **원리적 불가능이 증명된 유일한 접근**이다.

### 7.1 무엇을 만들었나

죽은풀이 실패했으니 "진짜 빈 공간"을 만들자는 발상. `tools/EXPAND_NSO.py`:

```
.rodata 를 N(페이지 배수) 만큼 확장  →  .data + bss 전체를 뒤로 이동
                                    →  data/bss 를 가리키는 모든 참조를 +N 갱신
새 영역 = rodata 확장부 (VA 0x5a68e68~) = 아무도 안 쓰는 진짜 빈 공간
```

`flags = 0`(무압축·무해시)이라 물리적으로 가능했다. 갱신해야 할 참조는 다음과 같았고,
**하나라도 빠지면 즉시 크래시**했다:

| # | 대상 | 규모 | 비고 |
|---|---|---|---|
| 1 | `DT_RELA` r_offset / r_addend | 802,618 엔트리 | RELACOUNT(800,482)보다 많음 |
| 2 | `DT_JMPREL` (PLT) | 857 | **처음 누락 → CPU write 크래시** |
| 3 | `SYMTAB` st_value | 30 | data를 가리키는 심볼 |
| 4 | `.dynamic` 주소값 | PLTGOT·INIT_ARRAY·FINI_ARRAY·dynamic 자체 | dynamic 자신도 data(0x64e8620) 소재 |
| 5 | `MOD0` 필드 | dynamic·bss_start·bss_end·**module_object** | **module_object 누락 → 2차 write 크래시** |
| 6 | `.text` `ADRP` 페이지 | **249,520개** | N이 페이지 배수라 immhi/immlo만 재인코딩, ADD/LDR offset 불변 |

`ADR`/`LDR-literal`의 data 참조는 0임을 assert로 확인. `INIT_ARRAY` 내용은 RELA가 처리.

**초반 플레이는 완벽히 정상이었다.** 마이라이프 완성 문장이 제대로 출력됐고 유저 테스트도 통과했다.
v1.2 / v1.3으로 릴리즈까지 나갔다.

### 7.2 그리고 28일차에서 죽었다

**증상**:

```
UndefinedInstructionException @ 0x000000000c58adcf   (opcode 0xe78d99e9)
```

두 가지가 결정적이었다:

- **주소가 4바이트 미정렬**(`% 4 == 3`) — ARM64 명령어 주소일 수 없다.
- **opcode `0xe78d99e9`가 UTF-8 한자 바이트** — 즉 tsv로 인코딩한 한글 문자열이다.
  → **CPU가 대사 문자열을 명령어로 실행하고 있다.** 실행 흐름/포인터가 오염됐다.
- 매 실행 **동일 주소**(완전 결정적).

### 7.3 이분법 격리 — EXPAND 자체가 범인

| 빌드 | 결과 |
|---|---|
| 확장 ON + exe_ext(리다이렉트) 적용 | 28일차 사망 |
| 확장 ON + **exe_ext 0건** | **동일 주소로 사망** → 마이라이프 리다이렉트는 무죄 |
| **비확장** (`main-noexpand`, md5 `f30983f3`) | **28일차 통과 + 이후 야구 경기까지 정상** |

`exe_ext`의 ents 22,485개는 전부 유효 RELA임을 재확인했고(범위·24B 정렬·`r_info==0x403`·
addend가 문자열 영역), RELA/JMPREL/SYMTAB/.dynamic/MOD0/ADRP 갱신도 전부 재검증 통과했다.
"ADRP 상한 누락" 가설도 오탐 0으로 기각(page ≥ data가 249,520, 상한 추가해도 249,520).

### 7.4 원인 규명 — 왜 원리적으로 불가능한가

크래시 주소 X를 역산했더니: **게임이 옛 주소로 함수 포인터를 읽고 있었다**
(X − N 슬롯에 '발전' 이라는 문자열이 있었다 — 이동 전 주소를 그대로 쓴 것).

X를 전 바이너리에서 수색한 결과:

> **`.rodata` 안에 RELA가 붙어 있지 않은 절대 data 포인터가 존재한다.**

즉 게임이 주소를 **저장된 재배치 가능 포인터가 아니라, 코드 즉치나 직렬화 데이터에 박힌
모듈 상대 오프셋으로 계산**하는 경로가 있다. 그런 경로는 재배치 테이블에 나타나지 않으므로
정적으로 전수 갱신할 방법이 없다.

그리고 결정타: **그런 값(= data 범위로 해석 가능한 8바이트)이 바이너리 안에 939,480개** 있다.
대부분은 우연이고, 어느 것이 진짜 포인터인지 **정적으로 판별 불가능**하다.

→ **`.data`를 옮기는 어떤 방식도 크래시한다. EXPAND는 원리적으로 불가능.**

### 7.5 조치

- `BUILD_FROM_MASTER.py`의 **기본 동작을 비확장으로 롤백**(`--expand`는 옵션으로만 남김. ⚠ 재발 주의)
- `EXPAND_NSO.py`는 폐기됐으나 참고용으로 저장소에 남아 있다 — **쓰지 말 것**
- `exe_ext` 섹션은 마스터에 보존(대체 공법에서 재사용됨)
- ⚠ **이미 릴리즈된 v1.2 / v1.3은 EXPAND를 포함하므로 사용자도 28일차에서 죽는다.**
  비확장 기반 긴급 릴리즈가 필요했다.
- 최종 대안 = **꼬리풀 공법**(파일을 늘리지 않고 리다이렉트). 5,244/5,244 수납, 스킵 0.
  main md5 `3ef0843d`, 크기 106,034,273B = 28일차 통과 구조(`f30983f3`)와 동일 구조.

> **교훈 1**: **확장/재배치는 초반 부팅·플레이만으로 검증할 수 없다.**
> 게임 후반 코드 경로가 놓친 참조를 밟는다. 28일차까지 가야 나온다.
> **교훈 2**: 죽은풀에 이어 EXPAND도 실패 — **이 게임에서 exe의 구조를 바꾸는 것 자체가 고위험**이다.
> 남은 유일한 안전 지대는 "**크기 불변 + 문자열 영역 in-place + 정렬된 RELA addend 재포인팅**" 뿐이다.
> **교훈 3**: 릴리즈 전 테스트 시나리오에 **장기 진행(마이라이프 28일차 이상, 실제 경기 플레이)** 을 포함하라.

## 8. 씬 추출 오버리치 — UI 항목까지 한 문장으로 뭉침

**증상**: 마이라이프 28일차 도달 시 게임 멈춤. 설정 화면·메뉴가 깨짐.

**원인**: 대본을 **RELA 연속 슬롯 런**으로 추출하는데, 연속 슬롯에는 이어지는 대사만 있는 게 아니다.
**독립 UI 항목·메뉴 라벨·설정 설명·분기 대사**도 나란히 놓인다.
이걸 "한 문장의 조각들"로 오인해 완성 문장을 첫 슬롯에 몰아넣고 나머지를 빈 문자열로 만들었다.

예시:
- `投球の体感スピードを「おそい」/「ややおそい」/「ふつう」…` — **설정 옵션 5개**가
  폭 224(10줄)짜리 한 덩어리로 뭉침
- `자동개별 설정 + 자동 구매 없음 + …` 메뉴 항목들이 한 문장으로
- 데이트/쇼핑 **분기 대사**(조건별 택1)가 전부 연결됨

**조치**: `CANCEL_BAD_EXT.py` — 확실한 것만 **79건 리다이렉트 취소**.

| 기준 | 건수 | 근거 |
|---|---|---|
| **A. 인자 시퀀스 위반** | 5 | 완성 `ko`의 `%s/%d`가 첫 조각이 공급받는 인자 수를 초과/타입 불일치 → **스택 오염 = 크래시/멈춤 유력**. 예: `%s%d回参考完全試合の快投`(인자 2) ← 완성 문장 인자 3 |
| **B. 대사창 초과** | 64 | 완성 폭 > 72(3줄). 최대 267폭(12줄) |
| **E. 첫 조각 = 전각 공백 슬롯** | 10 | 공백 슬롯에 완성 문장 주입 → 레이아웃 파손 |
| ⚠ F. 첫 조각 = 루비 슬롯 | **1,171 (취소 안 함)** | v1.2에서 "입단회견" 정상 표시 확인됨. 취소하면 22% 후퇴 |

취소 = `exe_ext`에서 제외 = 리다이렉트 안 함 = 원본 조각 그대로 표시(검증된 v1.1 동작).
검증: 취소 79건의 420슬롯 전부 원본 유지, 복원 후 「느리게」/「약간 느리게」/「보통」 옵션 정상 분리.
`exe_ext` 5,348 → 5,269. 배포 main `b089a32c`.

**추가로 꼬리풀 공법에서 25건 더 제외** — `ents`의 RELA 간격이 24가 아니면(비연속)
사이에 구분 슬롯이 있다는 뜻이고, 이는 별개 UI 필드(제목/프롬프트/내레이션)다.
이어붙이면 필드가 깨지므로 리다이렉트 대상에서 뺀다 (`BUILD_FROM_MASTER.py`의 멀티필드 검사).

⚠ **28일차 멈춤 이벤트를 직접 특정하지는 못했다**(Ryujinx 로그 비활성 + 스크린샷 없음).
결과적으로 이 수정으로는 안 고쳐졌고, 진범은 §7의 EXPAND였다.

> **교훈**: RELA 연속 슬롯은 **표시 순서는 맞지만 "한 대사"라는 보장은 없다.**
> 연속성만으로 문장 경계를 추론하지 말고, **스트라이드 균일성 + 인자 시퀀스 + 폭 검사**로
> 반드시 걸러라. 특히 **인자 개수 위반은 크래시**다.
> 그리고 **원인 미상인 크래시에 "그럴듯한 수정"을 내놓고 해결됐다고 믿지 마라** — 격리 실험이 우선이다.

## 9. 적대적 검증으로 잡은 것들

꼬리풀 공법은 배포 전에 **적대적 검증 2회**(4개 렌즈: 참조 잔존 / 할당 경계 / 렌더 의미 / 재빌드
재현성)를 거쳤다. 1회차에서 **치명 결함 3건**이 나왔다 — 전부 배포됐으면 크래시나 화면 파손이었다.

### 9.1 죽은조각 재사용이 UI 문자열을 파괴

리다이렉트로 인해 RELA 참조가 전멸한 조각 문자열을 "이제 아무도 안 쓰니 큰 청크로 재활용하자"고
판단했다. 그런데 그중에 **코드가 `ADRP + ADD` 즉치로 직접 주소를 계산해 참조하는 UI 문자열**이
16개 이상 섞여 있었다 — 세이브 확인창, 도감(図鑑) No 라벨 등. RELA만 봐서는 절대 안 걸린다.

**조치**: 죽은조각 풀 **전면 폐기**. 리다이렉트는 하되 **조각 바이트는 그대로 보존**한다.
동시에 보호셋에 **`.text` 코드 즉치 타깃**을 5번째 항목으로 추가:

```python
is_adrp = (text & 0x9f000000) == 0x90000000
# 뒤 8워드 안에서 같은 레지스터를 쓰는
#   ADD imm  : (w & 0xFFC00000) in (0x91000000, 0x91400000)   # sh=1이면 imm<<12
#   LDR/STR  : (w & 0x3B000000) == 0x39000000                  # offset = imm12 << size
```

과수집(over-collect)이 원칙이다 — 잘못 보호해서 잃는 건 몇 바이트지만,
못 보호하면 게임이 죽는다.

### 9.2 후행 NUL 런이 인접 바이너리 테이블의 0-프리픽스였다

꼬리풀을 처음엔 `[kr_end+1, jp_end + T)` 로 잡았다(후행 NUL 런 T까지 포함).
그런데 그 0들이 **문자열의 패딩이 아니라, 바로 뒤에 붙은 바이너리 테이블의 0-프리픽스**인
경우가 있었다. 거기에 문장을 쓰면 그 테이블이 오염된다.

**조치**: 풀 상한을 **`jp_end` 로 엄격히 제한**. 후행 NUL 런은 완전 제외.

```python
lo = off + kl + 1
hi = jp_end          # ⚠ off + jl + T 가 아니다
```

풀 용량은 줄었지만(758KB, 청크 평균 13B) 비대칭 분할 패킹으로 5,244문장 전량을 수납했다.

### 9.3 그 외

- `APPLY_MASTER.py`의 인자 전달 버그(1회차)
- 2회차에서 major 1건: **멀티필드(비연속 ents) 오정렬** → §8의 25건 제외로 수정
- 코드 즉치 스캔의 gap(윈도우 8워드를 벗어난 ADD 페어)은 "NUL 뒤 바이트만 해당하므로 무해" 판정
- 2회차 크래시 결함 **0건**

> **교훈**: 정적 분석으로 "안전하다"를 주장할 때는 **반드시 반대 입장에서 반증을 찾는 별도 검증**을
> 붙여라. 이 프로젝트에서 배포 전에 잡은 치명 결함은 전부 적대적 검증에서 나왔다.
> 그리고 **RELA만 보고 참조를 판단하지 마라** — 코드 즉치(`ADRP+ADD`)와 `base+index` 접근이 있다.

## 10. 분기 대사 — 현재도 미해결

**증상**: 전체 조합형 대사 리다이렉트(`main-all-exp`, 4MB 확장, 31,236문장)를 넣었더니
부팅은 정상인데 **상당수 대사가 여전히 조각 조합**으로 보였다("라면대활약고") + 조사 병기("이／가").

**원인**: **분기 대사**. 대사 슬롯 포인터 배열(base `0x5d3d440`, **112,352 슬롯**)에
여러 분기가 **연속으로** 저장되어 있고, 게임이 조건에 따라 **문장 중간 슬롯부터 렌더를 시작**한다.
→ 문장 첫 조각에 걸어둔 리다이렉트가 **아예 보이지 않는다.**

진입점은 이벤트 스크립트(`LIFESNR` `BIN00` 바이트코드)가 참조하는 인덱스인데,
**정적 해독에 실패**했다(자기 참조 포인터 8,789개를 찾았으나 코치 진입점 `0x5d45ea0`을
가리키는 것은 없었다). 동적 분석 — 게임 실행 중 슬롯 주소를 실측 — 이 필요하나
작업 PC에 게임이 없어 진행 못 했다.

**현재 상태**: **미해결.** 유저 지시로 리다이렉트 확대를 포기하고 최소 수정 노선으로 갔다.

- ⚠ 참고: **`이／가` 슬래시 노출은 전체 리다이렉트(`main-all-exp`)의 부작용**이고,
  마이라이프만 리다이렉트한 v1.2에는 **0건**이다. 즉 범위를 좁히면 부작용이 없다.
- `FIX_JOSA.py`(B안, 최소 수정): 조사 병기 `이(가)` / `을(를)` **744건 중 앞 글자가 한글인 88건만**
  받침 기준으로 확정(돌격대장이 / 외야수가). 변수 `%s` 뒤 653건은 판정 불가라 병기 유지.
  → v1.3 (main-b, md5 `f3cd5416`)
- 분기 대사의 조각 밀림은 **게임 구조상의 한계로 잔존**하며 릴리즈 노트에 명시했다.

> **교훈**: 리다이렉트는 **"문장의 시작이 항상 첫 조각"** 이라는 가정 위에 서 있다.
> 이 가정이 깨지는 분기 대사에는 쓸 수 없다.
> 해결하려면 이벤트 바이트코드 해독 또는 동적 분석(에뮬레이터 메모리 관찰)이 필요하다.
> **적용 범위를 좁게 유지하면(마이라이프 한정) 부작용이 없다** — 넓히기 전에 진입점부터 풀어라.

## 11. 기타 함정 (짧게)

### 11.1 줄 규칙 위반 — 밀림/잘림

한 줄 전각 24자, 대사창 3줄(폭 72). **원문이 차지하던 줄 수보다 번역이 더 많은 줄을 쓰면 위험**하다.

- exe: `_line_over.json`에 **6,763건 위반** 수집 → 축약 워크플로 → 6,755건 in-place 주입
  → main-c (md5 `fecd8797`). 잔여 폭 초과 8건(확장 영역 특수, 미미)
- RDB: `SCAN_RDB_LINE.py`로 폭 초과 1,472건 수집 → **줄 수(ceil) 기준 실질 밀림 460건**만 추림
  (`ブラバン→브라스밴드` 처럼 절대 폭이 작은 건 제외) → 19배치 축약 → `REINJECT_RDB_LINEFIT.py`
  로 4개 파일만 재주입(재배치 0, 크기 불변 → RDI 불변). 대상: `SEN_TEXT`, `SEN_TEXT_2ND`,
  `OL_VS_CHAMP`, `SCS_SC3_CMD`
- ⚠ 가나 판정 시 **중점 `・`(U+30FB)를 가나로 오탐**하지 말 것 — 음절만 셀 것

> **교훈**: 폭 초과 절대 건수가 아니라 **줄 수 증가 여부**로 우선순위를 매겨라.

### 11.2 추출 필터가 만든 대량 누락

추출 게이트를 잘못 잡아 통째로 빠진 텍스트가 여러 번 있었다.

| 누락 | 원인 | 규모 |
|---|---|---|
| **순한자(가나 0개) 문자열** | "가나 포함" 게이트가 순한자 UI 라벨을 전부 배제 | exe 신규 **9,144개** (発掘力/監督契約/球種選択/雨天中止 등) |
| **코드 참조 전용 문자열** | 추출기가 "데이터 포인터 참조"만 수집 → `ADRP+ADD`로만 쓰이는 UI 라벨 누락 | 2,101건 중 1,539 복구 (投手/決定/所持数) |
| **루비(후리가나) 슬롯** | 씬 추출이 RELA 연속 런 기반이라 런 밖 루비 슬롯은 통째 누락 | 1,904건 수집 → 루비 잔존 756→0, 가나 잔존 160→0 |
| **신규 연도 데이터** | `SEN_TEXT_2ND`(2025 소개문)는 추출 원본에 아예 없던 신규 파일 | 고유 1,706건 |

증상은 항상 같다 — **미번역 한자가 ADD 폰트에 의해 "깨진 한글"로 렌더된다.**
`投手` → "톳쇨", `決定` → "룩쾨", `所持数` → "쎄생웃". (tsv_inv 시뮬레이션이 관측과 정확히 일치)

⚠ 결정적으로: **원본과 동일한(주입 이력 0인) 슬롯은 diff 기반 패스가 전부 스킵한다.**
미번역 수색에는 `COLLECT_UNTRANSLATED.py` 같은 **절대 스캔**(전 슬롯의 NUL 문자열 중
tsv 디코드 후에도 가나가 남으면 미번역 판정)이 필요하다.

> **교훈**: 추출 게이트는 **누락을 만든다**. 배포본에 대한 **절대 스캔 안전망**을 항상 마지막에 돌려라.
> "가나가 남아 있는가", "`／` 슬래시가 남아 있는가" 같은 잔존 스캔이 최종 방어선이다.

### 11.3 재배치 이력 충돌로 슬롯 손상

`SEN_TEXT.CHK`(2024 선수 소개문) 배포 슬롯의 헤더가 깨지고 `csize`가 쓰레기값이었다
(과거 재배치 이력 충돌 추정). 게임이 로드에 실패해 소개문이 아예 표시되지 않았다.
`SEN_TEXT_FIX.py`로 원본 body를 재구성해 복구.

> **교훈**: 재배치는 투명하지만 **여러 번 겹치면 슬롯 헤더가 상할 수 있다.**
> 빌드 후 전 슬롯 무결성 검사(복호 + zlib 해제 성공 여부)를 돌려라.

### 11.4 비결정적 md5

`set` 순회 순서가 해시 랜덤화에 의존해 같은 입력에서 다른 바이너리가 나왔다.
dedup 정렬에 **결정적 tie-break `key=(-len, bytes)`** 를 붙여 해결.

> **교훈**: 빌드는 결정적이어야 한다. 같은 마스터 → 같은 md5가 나오는지 매번 확인하라.

### 11.5 배포 스크립트 인코딩

한글 `패치적용.bat`을 UTF-8(BOM 없음) + LF로 저장했더니 사용자 PC에서
`'t'은(는) 내부 또는…` 이 연발하며 파싱이 붕괴했다. cmd 파서가 줄/바이트 경계를 잘못 자른 것.

- **배포용 BAT는 반드시 CP949 + CRLF**
- **실행파일 호출은 `.\` 접두** (`.\xdelta3.exe`) — `NoDefaultCurrentDirectoryInExePath` 정책 PC 대비
- 검증은 TEMP의 ASCII 경로에 원본을 **하드링크**(6.6GB 복사 회피)하고 실행 → 산출물 md5 대조

### 11.6 성능·환경 잡학

- REPACK은 매 실행 6.6GB `shutil.copy2` 가 병목(드라이브 ~70MB/s HDD급) → `robocopy /J`(96s)
  또는 `--reuse`(13.7s). ⚠ **PowerShell에서 robocopy는 exit 1 = 성공**
- `EXE_SPACE_STRIP` 최초 구현이 O(n²)(`bytes(buf).find` 700만 회)으로 멈춤 → 세그먼트 시작 `set`으로 최적화
- 격리 테스트 원칙: **폰트 / 텍스트 / exe 를 한 번에 하나씩만** 바꿔 배포하라.
  이 프로젝트의 크래시 원인은 전부 이분법 격리로 찾았다.
- 릴리즈된 자산은 **교체하지 말고 새 태그**로 낸다(xdelta는 원본 md5에 묶여 있다).

## 마지막으로: 현재의 안전 경계선

이 모든 실패 끝에 남은, **검증된 안전 구역**은 다음뿐이다.

1. **파일 크기 불변** — exe도 RDB 슬롯도 늘리지 않는다(RDB는 재배치+RDI 갱신까지만 허용).
2. **문자열 영역(`> 0x3d2551d`) in-place 치환만** — 원문 + 후행 NUL 슬랙 예산 안에서.
3. **RELA `r_addend`의 24바이트 정렬 재포인팅** — 이것만이 유일하게 허용된 구조 변경.
4. **`.text` / `.data` / 헤더 / 동적 영역은 바이트 불변** — 빌드가 assert로 강제한다.

이 밖으로 나가려는 모든 시도(zero-run 풀, 죽은풀, 세그먼트 확장)는 **전부 실패했다.**
새로운 공간이 필요하다면, 먼저 §7.4를 다시 읽고 **왜 정적 판별이 불가능한지**부터 이해하라.
